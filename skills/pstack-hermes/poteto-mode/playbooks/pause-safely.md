### Pause safely

**You own a clean stop. Leave a checkpoint a cold-start agent can resume from.** Pause on an explicit stop or when safety, budget, or runtime failure requires it. "Keep going" means continue within the actual grant, not beyond safety boundaries.

1. Stop at a safe boundary. Finish the current atomic step or back out of only your partial step. Start no new work. Stop new dispatches. Native delegated children are process-local and cannot be treated as a resumable fleet. Use the installed runtime's documented cancellation controls if available; do not invent a message/cancel API. For separately launched terminal profile runs, use `process_manage` to stop owned jobs after preserving their artifacts. If cancellation cannot be confirmed, record that fact and quarantine the scope rather than giving it to a second writer.
2. Take no irreversible or external action merely to pause. No new PR, push, merge, deployment, message, data deletion, or force-push without existing authorization. Having opened a PR earlier is not blanket permission to publish a checkpoint.
3. Make work durable within scope. Inspect the tree and exact owned paths with `terminal`. If local commits are authorized, stage only those paths and make one clear `wip:` checkpoint commit. If broken, say so in its body. If commits are forbidden or unrelated work is mixed in, preserve an owned patch and untracked-file copies in the approved durable store instead. Do not use a hard reset or stash another owner's work.
4. Write a resume note with `write_file`. Include intent, current action, progress and verification, branch/worktree and SHAs, owned files, pending jobs, allowed actions, next command, and gotchas. Point to a `skill_view(name='show-me-your-work')` trail rather than duplicating it. Use an approved durable project/profile-scoped store for a real handoff. A short compaction note can live at `$TMPDIR/<slug>-resume.md`, but scratch retention is not a durable backup. Never store secrets in the note.
5. Confirm the checkpoint artifact exists and account for all in-flight work before claiming a clean pause. A terminal job started with `persist_on_release=true` keeps running across session cleanup, so explicitly stop or hand off each such job rather than assuming teardown handles it. That flag never guarantees host-restart survival.

**Reply:** loop position, on-disk paths, checkpoint commits or patch, whether the tree is clean, any unconfirmed running work, and the first action on resume. This is a pause, not a completed-task report.
