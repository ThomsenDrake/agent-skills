### Opening a PR

Use at the end of an implementation playbook only when publication is authorized. Investigation and planning do not open PRs. Opening a PR does not authorize babysitting or merging it.

**Worktree.** Discover the actual repo, base branch, dirty state, and project rules with `terminal`, `search_files`, and `read_file`. Use an isolated git worktree when concurrent writers or existing unrelated edits make it necessary. Create scratch worktrees under `$TMPDIR` or an approved worktree directory. Give each writer its exact worktree and allowed files. Native `delegate_task` isolates conversation and terminal context, not repository writes; it does not create a worktree or make shared-branch writes safe. Do not reset a dirty branch or use a hard reset between workers. Preserve unrelated work and move only owned changes to a clean worktree after inspection.

**Commits.** When authorized, commit verified units liberally and stage exact owned paths. Reorder into small, ordered commits before opening the PR. Each slice tells part of the story and is independently explainable. Amend only a just-made owned commit when appropriate; use a new commit for separable work. Do not rewrite published/shared history without the required grant. Commit bodies do not restate subjects.

**Cleanup before commit.** Inspect the real diff. Remove generated boilerplate, redundant guards, speculative abstractions, unused imports, and comments that narrate code. Preserve load-bearing checks and behavior. Run the repo's formatter, lint, typecheck, and tests with `terminal`. There is no required external cleanup plugin. A code leaf may do ordinary cleanup and return check receipts; independent reviews belong to the parent gate below. Write titles, descriptions, and commit bodies under `skill_view(name='technical-writing')`, then apply `skill_view(name='unslop')`. Use one word per action, keep articles, and prefer a plain verb over an unnecessary `-ing` form.

**Mandatory parent-owned delegated-PR gate.** Every delegated PR must pass `interrogate`, cleanup, and `no-comments` before any PR-facing publication, including creating or marking ready a PR and pushing updates to an existing PR. This is mandatory even when design review would otherwise be optional.

1. Give the bounded code delegate only implementation, ordinary cleanup, and local checks. Require its exact local head or diff snapshot, changed paths, cleanup diff, and actual check receipts, then have it return without publication. Do not ask a code leaf to run `interrogate` or `no-comments`; both review workflows need parent-owned delegation, which flat leaf workers may not have.
2. After the code delegate returns, the parent loads `skill_view(name='interrogate')` and `skill_view(name='no-comments')`. The parent follows their protocols and dispatches independent reviewer leaves itself, with the exact stable snapshot, complete scoped instructions, and no publication authority. These reviewers are siblings of the code leaf, not its children; no recursive worker tree is assumed. Run the interrogate panel, inspect and accept the cleanup diff, then run the independent no-comments audit.
3. Inspect the actual reviewer evidence and scoped checks. Default no-comments to audit-only. Preserve legal headers, public contracts, and build-required safety directives. Return accepted in-scope fixes to a fresh bounded implementation phase, then recheck cleanup, tests, and affected independent reviews on the resulting snapshot before accepting the gate. Do not accept stale verdicts or silently widen edit authority. Only the parent or an explicitly authorized later publisher may publish the accepted snapshot and report its URL/head readback.
4. If delegation, required role instructions, or independent reviewer evidence is unavailable, report the publication gate blocked. Do not substitute self-review, claim a panel ran, or publish while a mandatory gate is incomplete.

**Titles.** Use Conventional Commits, `type(scope): subject`, with no trailing period. Types include `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, and `perf`. Scope names the area. The subject is short and imperative, and names a real symbol when it carries the change, such as `fix(pstack): retarget opening-a-pr babysit trigger`.

**Descriptions.** The body is a one-minute briefing for someone who has the diff, not a lab notebook. Say why it exists, what it excludes, what could break, and how you proved it works. Use short sentences. The body may become the squash commit body, so keep it under about 40 lines. Use these `##` headings in order and omit empty optional sections.

- `## Why`. The problem and approach in 1 to 3 short sentences. No SHA or rebase genealogy preamble.
- `## What changed`. 1 to 3 short bullets. Name a path or symbol only when it carries the change. Name both sides of a rename or retarget.
- `## Scope`. Always present. 1 to 3 short items about coverage and deliberate exclusions, not a file-by-file essay.
- `## Tradeoffs`. Only rejected alternatives a reviewer would otherwise ask about.
- `## Blast Radius`. 1 or 2 sentences about affected users and systems and the relevant risk. If trunk is red, state the cost of leaving it red.
- `## Verification`. 1 to 3 actual run paths and outcomes. For performance, give one primary number with its unit, `before -> after`, and a link to full artifacts. No invented runs, sample-size essay, or lane table here.

Attach screenshots or videos when they prove a claim. Put full SHAs, lane receipts, metric tables, and verdict detail in a linked artifact you actually created or read.

**Forge and dependencies.** Git and an authenticated GitHub CLI are the default dependencies. Check `terminal(command='gh auth status', workdir='<repo>')` without printing credentials. If the optional Origin CLI is installed and can resolve this repo, select it explicitly and keep that forge for all operations. Inspect its installed help instead of assuming flags. Never require Graphite. Hermes has no assumed built-in PR integration. If a real available integration tracks PRs, inspect its schema and use it for operations it owns; otherwise use `terminal` with the selected forge. Do not mix incompatible status sources.

**Size and stacks.** Prefer narrow PRs. A stack is a base-branch chain. The root targets the actual trunk; each child starts from its parent's exact tip and targets the parent branch. Independent work branches from trunk. One topology owner performs authorized rebases and retargets. For GitHub, create through `terminal(command='gh pr create --base "<base-branch>" --title "<title>" --body-file "<body-file>"', workdir='<repo>')`. Write the body with `write_file`; do not interpolate untrusted text into a command. A child uses its parent's branch as `--base`. Retarget only with authority, through `terminal(command='gh pr edit <pr> --base "<parent-branch>"', workdir='<repo>')`. Load `skill_view(name='poteto-mode', file_path='playbooks/shipping.md')` for the post-merge move to trunk.

**Readiness and readback.** Open ready, not draft, unless the user explicitly requested a draft. With `gh`, omit `--draft`. With an available integration, set `draft: false` explicitly. With Origin, confirm its ready/open flag in help. If the result is unexpectedly draft, mark it ready only within the publishing grant. After creation, edit, or readiness changes, read the exact PR back through `terminal(command='gh pr view <pr> --json url,state,isDraft,headRefOid,baseRefName', workdir='<repo>')` or the selected forge's equivalent before claiming status. Run checks on the committed head before a PR-facing push, with hooks enabled. Verify remote head after a push.

**Babysit.** Opening does not start it. Post the URL and continue the authorized phase or stack. A separate babysit starts on the user's request, normally after the stack exists. Load `skill_view(name='poteto-mode', file_path='playbooks/babysit.md')`. A bounded code delegate returns local implementation/cleanup/check receipts before the mandatory parent-owned delegated-PR gate above. The parent reports the actual URL/head only after that gate and authorized publication. The leaf does not keep a watcher alive after returning. An Autopilot owner has babysitting assigned explicitly in its brief, but the coordinator owns long-lived watchers and dispatches later owner phases. A grant to build a PR is not a grant to merge.

**Reply:** PR URL, scope, actual verification outcomes, ready/draft status and current head from readback, plus any remaining review or operator gate.
