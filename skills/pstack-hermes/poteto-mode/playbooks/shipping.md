### Shipping

**One-shot launch gate.** Before any profile-process launch here, load `skill_view(name='pstack-hermes', file_path='references/one-shot-safety.md')`. `-z` bypasses command and hook approval gates. Require explicit authorization for that bypass, review inherited hooks, and verify restricted execution boundaries, scoped credentials, and minimal toolsets. Model-diversity or unattended-work requests are not bypass authorization. Otherwise use bounded parent-driven delegates, an approval-preserving interactive session, or report blocked.

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the stack.** This playbook requires explicit landing authority for the named PRs. It never grants approval bypass, deployment, secret access, messages, or unrelated merges.

1. **Resolve the forge and independently verify every PR.** Git and authenticated `gh` are the default dependencies. Select optional Origin only after checking installed help and repo resolution, then keep that forge throughout. Never require Graphite or a cloud-agent service. Assign one verifier that did not author the code per PR. Use `delegate_task(tasks=[{'goal': '<verify PR and parent against head>', 'context': '<repo and isolated worktree, exact SHAs, real-surface driver, acceptance, no edits/merges, artifact/report contract>'}])` when available. Children inherit the parent model and are isolated contexts, not different-model evidence. For actual model diversity, use only operator-configured named profiles through `terminal(command='hermes -p <profile> -z "<bounded verification brief>"', workdir='<isolated worktree>')`. Without an independent verifier, report that gate blocked rather than calling self-review independent.

   Run the change as a user would using the repo's CLI/UI harness through `terminal` or available Hermes browser/computer-use tools. Discover optional driver dependencies first. Compare parent and head under matched conditions. Each report names exact SHAs, commands, actual output, artifacts, and `PASS`, `PASS+NOTES`, or `FAIL`. Findings that affect correctness cannot hide as notes. Inspect receipts yourself before accepting a verdict. Green CI or an approving bot is input, not this real-surface verdict. Post a verdict to the PR only when comment posting is authorized, then read the exact post back; otherwise keep it in the approved artifact store and link it in the report.
2. **Find the contiguous verified run rooted at the bottom.** Walk from the lowest unmerged PR and stop at the first without an accepted `PASS` or `PASS+NOTES`. The top verified PR below that gap is the ceiling. Verified work above a gap waits. A branch that neither holds nor needs lower code can move to trunk only with topology authority and a fresh verdict, since its old environment included that code. Record the immutable PR list, base chain, heads, verdict authors, and evidence.
3. **Check that verdicts still cover the code.** A verdict covers a patch, CI covers a head, and an unchanged patch alone does not prove unchanged runtime context. Through `terminal`, compare stable `git patch-id` values for the verdict-time parent/head patch and the current parent/head patch. Also inspect base/dependency drift and merge-result behavior. Carry a lane result only when the patch and relevant context remain equivalent. If changes are limited to tests/docs/lint config, a build-producing lane may carry only if the exercised output is identical apart from documented noise. Noise must also occur between two builds of the verdict SHA, or be an embedded SHA. Name each noisy file. The changed checks and docs still get fresh verification/review. A dev-server lane without comparable build output reruns. Re-verify everything else that drifted.
4. **Land bottom-up one PR at a time.** Re-read the exact lowest PR immediately before merging. It must target actual trunk, have an accepted current verdict for its exact `headRefOid`, pass current checks and required reviews, and be within the grant. Set `<verified-head-sha>` to that full accepted SHA, not a branch name or a freshly observed but unverified head. Never merge a GitHub child while it still targets its parent's branch. For GitHub, use `terminal(command='gh pr merge <pr> --squash --match-head-commit <verified-head-sha>', workdir='<repo>')`. On a head mismatch or rejected merge, stop and reverify; never retry against a new head without an accepted verdict covering it. Never use an admin/protection bypass. For Origin, inspect installed help and require an atomic expected-head match for only the bottom PR. If the selected forge cannot enforce that condition, report landing blocked rather than substituting an unpinned merge. Read the exact target back with `terminal(command='gh pr view <pr> --json state,mergedAt,baseRefName,headRefOid,mergeCommit', workdir='<repo>')` or the selected forge equivalent. Require merged state, trunk base, and the accepted head before reporting success. A request or queue entry is not a completed merge.

   Do not arm auto-merge or submit queued landing under this workflow. A request-time head pin is not perpetual: a deferred merge can accept a moved head, and a promised writer freeze is not enforced immutable head semantics. Inspect branch rules and existing pending landing state first. If the merge command would enqueue or enable deferred landing automatically, stop at merge-ready without invoking it. A queue-only repository needs a separately approved service that enforces immutable head semantics and continuously current verdicts; until then landing is blocked. Never bypass its queue or branch protections.

   Only after actual merge, the topology owner retargets the next child to trunk, moves only that child's patch onto the merge result, and publishes the owned branch with a force-with-lease pinned to the last observed remote SHA when that rewrite is authorized. Never overwrite another writer's push. Read back the changed base and remote head. Apply step 3's patch/context rule, rerun current-head CI, and merge the next PR only when its gates clear. A conflict or changed behavior stops the landing and gets an explicitly owned fix round, not opportunistic stack surgery.
5. **Leave the stack alone while it lands.** Step 4's next-child move is the only authorized branch/base mutation. On GitHub, load `skill_view(name='poteto-mode', file_path='playbooks/babysit.md')` for watcher setup. With Bun and locked script dependencies available, resolve `<poteto-mode-skill-dir>` from `skill_view(name='poteto-mode')` and use `terminal(command='bun run "<poteto-mode-skill-dir>/scripts/watch-pr/watch-pr" --queued-stack --stack-prs <bottom-to-top> --timeout 1800', workdir='<repo>', background=true, notify=true)`. The list ends at the ceiling. Use `process_manage` for this parent-owned terminal job and read forge state after each event; timeout is a checkpoint, not a merge. Without the helper, use the selected forge's check-watch and exact PR readback. No extra sleep loop and no assumed durable child. An expected post-merge base move is not damage to repair. Investigate a stall before changing anything. On operator stop, disarm any authorized pending auto-merge/queue action if supported, verify that state, and stop writes.
6. **Stop at the ceiling.** Extending the run needs new verdicts and any additional landing authorization, so begin a new pass at step 1. Report incomplete queued or blocked work as incomplete.

For background delegation, do other independent work, then end the turn for Hermes completion delivery. Do not poll child transcripts. A returned verifier summary is unverified until its actual artifact and receipts have been checked.

**Reply:** verified run and ceiling, exact verdict and author for each PR, what actually merged and readback proof, what is merely queued, remaining gaps/gates, and artifact paths.
